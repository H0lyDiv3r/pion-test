Pion ICE Field Manual

A deep architectural reference covering NAT traversal physics, candidate matrices, cryptographic handshakes, and peer-to-peer audio streaming mechanics.

1. The Core Philosophy: Why Pion ICE?

When developers want to stream audio peer-to-peer, they are often directed to WebRTC. However, standard WebRTC introduces tremendous cognitive overhead: SDP offer/answer text blobs, browser state machines, DTLS handshakes, SCTP multiplexing, and media codec negotiation.

Pion ICE decouples NAT traversal from the data protocol. It does one job with mathematical precision:

The Pion ICE Promise
Punch through firewalls and home routers, find the fastest direct UDP path between two machines, and hand you a raw *ice.Conn socket. What you send over that socket is 100% up to you.

2. The Truth About STUN

A common fear is that using a STUN server requires an account, an API key, or ongoing server fees.

Mental Model: The Mirror
A STUN server is simply a mirror on the public internet. Your computer sends a 32-byte UDP ping asking: "What does my router's public IP and port look like to the outside world?" The STUN server reflects back: "You look like 196.191.61.180:52414." That conversation takes 5 milliseconds and is completely finished.

Zero bytes of your audio stream ever touch the STUN server. Because STUN is unauthenticated and uses negligible bandwidth, Google, Cloudflare, and others host free public mirrors: 

stunURI, _ := stun.ParseURI("stun:stun.l.google.com:19302")

When do you NOT need STUN? On a local Wi-Fi network, on a mesh VPN (Tailscale/WireGuard), or when running on localhost. Local host candidates connect directly without contacting STUN.

3. Demystifying Candidates

Why doesn't your computer just give the peer "its IP address"? Because your computer doesn't have one address—it has a Wi-Fi IP, a loopback IP, maybe virtual machine adapters, and a public WAN IP.

Mental Model: The Contact Card
An ICE Candidate is a single potential door to knock on. Sending your candidate list is like saying: "If you're in my room, knock on my door (Host). If you're across town, call my phone (STUN srflx). Try all my numbers and let's use the one that picks up first."

4. The Disconnect Mystery: Martian Filtering

In testing, you may observe the connection transition to Connected and then immediately drop to Disconnected after 5 seconds:

🏆 Selected Local: 127.0.0.1 (host) 🏆 Selected Remote: 172.20.0.1 (host) 🔄 [State Change]: Disconnected

Why did this happen? One peer picked Loopback (127.0.0.1), while the other picked a virtual container bridge (172.20.0.1).

The Linux kernel implements Reverse Path Filtering (Martian packet protection). While the initial STUN packet slipped through local route tables, subsequent 2-second background keepalive heartbeats crossing between loopback and bridge subnets were dropped by the kernel. After 5 seconds of silence, ICE declared the link dead.

The Solution: When testing on one machine, filter out virtual bridge interfaces so both peers select 127.0.0.1 $\leftrightarrow$ 127.0.0.1.

5. The Security Handshake: Why Dial Uses Remote Passwords

When you run agent.Dial(ctx, remoteUfrag, remotePwd), why do you pass the remote peer's credentials rather than your own?

Mental Model: The Secret Knock at the Door
Your peer's IP is exposed to the wild internet where bots and port scanners constantly blast random packets. To prove you are an authorized friend and not an internet scanner, your ping must speak their secret password.

Inside every STUN ping fired during Dial(), Pion embeds two security fields:

  1. USERNAME: Formatted as remoteUfrag:localUfrag ("Hey Bob, this is Alice knocking!").
  2. MESSAGE-INTEGRITY: An HMAC-SHA1 signature of the packet computed using remotePwd.

When the remote peer receives the packet, it validates the signature against its own password. If a random internet bot sends packets to that port, the signature check fails and the packet is silently dropped.

6. How the Winner is Chosen: The Priority Race

If both peers supply 10 candidates each, does Pion broadcast your audio to all 10?

The Myth: Broadcasting
No. Audio is never broadcast to all candidates. That would destroy bandwidth. All candidates compete in an audition, but exactly one candidate pair is hired for the job.

The 3-Step Selection Process

  1. The Matrix (Checklist): Pion multiplies local and remote candidates ($10 \times 10 = 100$ candidate pairs).
  2. Priority Sorting: Pairs are sorted by speed/cost:
    • Host $\leftrightarrow$ Host (LAN/Loopback) $\rightarrow$ Highest priority (0ms latency, zero cost).
    • srflx $\leftrightarrow$ srflx (Internet via STUN) $\rightarrow$ Medium priority.
    • relay (TURN proxy) $\rightarrow$ Lowest priority.
  3. The Race & Nomination: Pings are fired down the sorted list. As soon as the highest-priority pair succeeds, the Controlling agent stamps it with USE-CANDIDATE. That pair becomes Nominated, and 100% of all subsequent data travels exclusively over that single socket.

7. Host vs Listener Roles: Dispelling the Naming Confusion

Are "Host" and "Listener" official Pion concepts? No. They are purely arbitrary names we chose for our command line flags.

Pion ICE has only two real, functional roles:

Role in Pion Method What it actually does
Controlling Agent agent.Dial() The Decider. Initiates checks and chooses the winning pair with USE-CANDIDATE.
Controlled Agent agent.Accept() The Follower. Responds to pings and adopts the path chosen by the Controlling agent.

Can the audio streamer start first? Yes! In fact, in an audio app, the streamer starting first, generating an invite code, and letting the listener connect is the most natural real-world workflow.

8. Lifecycle Callbacks: Event Listeners

Functions like OnCandidate and OnConnectionStateChange are event listeners that you register once during setup:

  • OnCandidate: Fires multiple times as the local interfaces and STUN mirrors report addresses. When gathering is 100% complete, it fires one final time with c == nil.
  • OnConnectionStateChange: Stays active for the entire life of your program. It tracks the ICE state machine: New $\rightarrow$ Checking $\rightarrow$ Connected $\rightarrow$ Disconnected (temporary glitch) $\rightarrow$ Connected (self-healed!).

9. Sending Data: The 1-Byte Multiplexer

Because an *ice.Conn passes individual datagrams, you can prefix byte 0 with a type discriminator to send text, commands, and binary audio across the same pipe:

[ Byte 0: Tag ] ──► [ Bytes 1..N: Payload ] 'T' (0x54) ──► Plain Text string 'C' (0x43) ──► JSON Command: {"action":"PLAY","track":"song.mp3"} 'B' (0x42) ──► Binary Audio chunk (1200 bytes)

The UDP Audio Streaming Rules

  1. Keep chunks $\le$ 1,200 bytes: Packets exceeding the standard 1,500 MTU get fragmented or dropped by routers.
  2. Use a Metronome (Pacing): Do not blast files in a raw loop. For a 128 kbps MP3 (16 KB/sec), send 1,200-byte chunks on a time.Ticker(75 * time.Millisecond) to match real-time playback.

10. Scaling to 10 Peers

Because an ice.Agent is strictly 1-to-1, a Host streaming to 10 listeners creates 10 separate *ice.Conn sockets (a Star Mesh):

┌──► [ Listener 1 ] (conn #1) ├──► [ Listener 2 ] (conn #2) [ Host / Streamer ] ─┼──► ... └──► [ Listener 10 ] (conn #10)

Bandwidth Reality: 10 listeners on a 128 kbps audio stream consume only 1.28 Mbps upload. Any standard home broadband connection can effortlessly broadcast direct P2P audio to 10 listeners.
